# Намерение: антиабуз и лимиты по user_id (MAX-бот)

**Статус:** не реализовано, к выполнению позже.  
**Код:** `max_bot/` (точка входа обработки апдейтов — `dispatcher.py` → `handle_update`).

## Цель

Защита от флуда сообщений/callback одним или многими пользователями MAX: нагрузка на API MAX, Postgres, память (`lead_session._sessions`), спам в чаты отделов.

## Предлагаемая логика

1. **Место врезки:** начало `handle_update`, после извлечения `user_id`, до `handle_max_lead_message` и тяжёлых веток. При отсутствии `user_id` — как сейчас, без лимита.

2. **Алгоритм:** скользящее окно по счётчику событий на `user_id`:
   - хранить временные метки последних событий (например `collections.deque`);
   - удалять метки старше `now - WINDOW_SEC`;
   - если количество ≥ `MAX_EVENTS` → отказ (короткий ответ пользователю опционально, без БД и без рассылки в отделы);
   - иначе добавить метку и продолжить обработку.

3. **Что считать событием (минимальный вариант):** один тик на каждый проход `handle_update` с валидным `user_id` (и сообщение, и callback). При необходимости позже — раздельные лимиты для callback vs текст.

4. **Хранилище:** для одного инстанса `max-bot` — **in-memory** (`dict[int, deque]`), аналогично сессиям. При нескольких репликах — рассмотреть Redis.

5. **Конфигурация (env), черновик:**
   - `MAX_RL_ENABLED=1|0`
   - `MAX_RL_WINDOW_SEC=60`
   - `MAX_RL_MAX_EVENTS=30` (подобрать по реальной нагрузке сценария лида)
   - опционально `MAX_RL_BYPASS_IDS` — тестовые user_id

6. **При превышении:** не вызывать сохранение лида и `notify_max_department`; лог `WARNING` с `user_id` без полного текста/ПДн; при желании — одно короткое сообщение в чат раз в окно.

7. **Опционально позже:** глобальный лимит; TTL/очистка `_sessions`; маскирование ПДн в логах (см. обсуждение безопасности MAX-бота).
