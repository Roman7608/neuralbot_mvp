7. Время лидов (местное) и БД (2026-04)
---------------------------------------
• Проблема: created_at у лидов отставал на ~4 ч относительно Самары — Postgres
  писал CURRENT_TIMESTAMP в UTC, колонка TIMESTAMP без TZ; админка показывала
  значение как есть.
• Решение:
  - database/postgresql_manager.py: при выдаче соединения из пула выполняется
    SET SESSION TIME ZONE по postgresql_config.POSTGRESQL_SESSION_TIMEZONE
    (env POSTGRESQL_SESSION_TIMEZONE или TZ, иначе Europe/Samara).
  - postgresql_config.py: константа POSTGRESQL_SESSION_TIMEZONE.
  - docker-compose.yml: TZ для сервисов postgres и admin-panel (как у max-bot).
• Перезапуск: postgres, admin-panel, max-bot, telegram-bot после деплоя; образы
  ботов пересобрать, если менялся Python. Старые строки в telegram_leads сами
  не сдвигаются — только новые вставки.
• Ошибка 2026-04-03: флаг часового пояса вешали на conn._vikingi_session_tz_ok —
  у объекта psycopg2.connection нельзя задавать произвольные атрибуты →
  AttributeError при save_lead, в логах «MAX лид сохранён: ID=None», уведомление
  в чат MAX при этом уже ушло. Исправление: учёт id(conn) в множестве
  PostgreSQLManager._tz_applied_conn_ids (database/postgresql_manager.py).

8. Контакт MAX: vCard с переводами строк только \r (2026-04)
------------------------------------------------------------
• Симптом: в telegram_leads.client_phone попадал целый текст vCard (ez-vcard),
  а не +7…; TEL;TYPE=cell:… присутствовал, но не парсился.
• Причина: в extract_phone_from_vcard регулярка с (?m)^ ищет начало строки
  только после \n; MAX отдаёт vCard с \r без \n — все поля в одной логической
  «строке» для regex.
• Исправление: telegram_bot/utils/phone_normalizer.py — перед разбором vCard
  заменить \r\n и \r на \n. Этот модуль общий с Telegram-ботом; после правки
  пересобрать max-bot (и при необходимости telegram-bot).
• max_bot/dispatcher.py: extract_contact_phone читает message.contact (как в
  Bot API), int-номер приводится к str; если message_created похоже на контакт
  (поле contact или attachment type contact), но номер не извлечён — WARNING в
  лог с body_keys, att_types, msg_keys, text_in (без WARNING на каждое сообщение
  с inline_keyboard).
• phone_normalizer: строка из 11 цифр вида 7902… (без «+») раньше не
  нормализовалась → в логах «Не удалось нормализовать номер: 79023730808» и
  контакт MAX не принимался; добавлена ветка 7+9… (_normalize_phone_scalar).
• Проверка в работе (2026-04-04): после пересборки и деплоя max-bot сценарий
  «Поделиться контактом» (кнопка «Передать номер») — ответ бота, лид в админке
  и уведомление в чате MAX работают; регрессий по контакту не зафиксировано.

9. Диагностика «лид MAX не в админке»
-------------------------------------
• Запись в БД — только после успешного save_lead (в т.ч. из finalize_lead_max).
  Если диалог не дошёл до финализации (телефон не принят / не «Готово»), строки
  не будет.
• Проверка: SELECT … FROM telegram_leads WHERE source='max' ORDER BY id DESC;
• Логи: docker compose logs max-bot | grep «лид сохран» / «Ошибка сохранения».

1. Лиды и каналы
----------------

  (тот же том, что в compose).

3. Тексты и сценарии

• Приветствие GREETING: убрана фраза «Ниже — кнопка… как в Telegram-боте».
• Исправлена кнопка «Политика»: callback show_policy больше не подменяется текстом

4. Политика ПДн в MAX
---------------------
• Приоритет кнопки политики (keyboards._policy_button_row):
  1) если на диске есть локальный файл политики — callback; по нажатию файл
     загружается в MAX через POST /uploads?type=file и отправляется вложением
     (max_bot/api_client.py: upload_file_get_token, send_message_with_file);
     подпись к сообщению без «Полного текста…» — пусто / невидимый символ для API.
  2) иначе, если задан публичный URL — кнопка type=link (браузер).
  3) иначе — краткий текст из MENU_REPLIES.
• Повторы отправки при ошибке attachment.not.ready (обработка файла на стороне MAX).

11. Админка «Лиды» — голосовой бот: различать исход дозвона до людей в Викингах
    (требование к продукту, черновик; 2026-04)
--------------------------------------------------------------------------------
Важно: речь о лидах с источником «голосовой бот» (телефония, Asterisk, AudioSocket),
а не о сценарии MAX-бота в мессенджере. Запись ведётся здесь как единое требование
к разделу «Лиды» в админке (общая таблица telegram_leads: TG / MAX / phone).

Проблема: сейчас в колонке «Потребность» и тексте лида сложно отличить случаи:
  A) разговор с живым сотрудником Викингов реально состоялся;
  B) была попытка перевода на линию/оператора, но в Викингах трубку не взяли /
     не приняли разговор / сброс до ответа / иные причины без успешного human pickup.

Цель: в UI «Лиды» и при экспорте явно видеть класс исхода контакта (отдельная колонка
и/или нормализованное поле в БД), чтобы аналитика и отделы не смешивали «лид с
контактом» и «лид без дозвона до человека».

Предлагаемые варианты значений (можно сузить до 2–3 после согласования):

  Уровень 1 — кратко (минимум для фильтра):
    • human_contact_ok     — разговор с сотрудником Викингов состоялся (после перевода
      или прямой линии — уточнить критерий в коде: bridge/ANSWER на стороне оператора).
    • human_contact_failed — попытка дозвона до людей была; ответа сотрудника не было
      (таймаут очереди, занято, сброс клиентом ожидая оператора, отказ Asterisk и т.п.).
    • bot_only             — только диалог с ботом, до перевода на человека не дошли
      (в т.ч. «нерабочее время», завершение после сценария бота без transfer).
    • unknown              — нельзя определить по имеющимся логам/CDR.

  Уровень 2 — детализация для human_contact_failed (подтип или вторая колонка):
    • no_answer_timeout    — долго ждали, никто не ответил.
    • operator_busy        — линия занята / недоступна со стороны Викингов.
    • client_hangup_wait   — клиент положил трубку в ожидании оператора.
    • transfer_failed_tech — сбой перевода (AMI, канал, маршрутизация).
    • other                — прочее (текстом в примечании / need_text).

  Уровень 2 — детализация для bot_only (по желанию):
    • after_hours_bot_only — нерабочее время, только сценарий бота.
    • client_hangup_bot    — клиент завершил до выбора перевода.
    • completed_bot_flow   — сценарий бота завершён без запроса перевода.

Реализация (на будущее, не сделано в этом коммите документа):
  • Новое поле в telegram_leads, например contact_outcome VARCHAR + опционально
    contact_outcome_detail VARCHAR / JSONB; заполнять из voice-bot при финализации сессии
    по событиям перевода (см. voice_bot_transfer_events, AMI, при наличии — CDR Инфолады).
  • Альтернатива: не расширять схему, а жёстко кодировать префиксы в need_text /
    response_message — хуже для фильтров и отчётов.
  • Блок «Непринятые звонки» в админке — про вызовы, не дошедшие до бота; это ортогонально
    настоящему требованию (здесь — дошли до бота, но не до человека после перевода).

Согласование: выбрать минимальный набор меток (рекомендация: начать с уровня 1 из
четырёх значений + поле «комментарий» для саппорта).
