Организация информации в веб-админке Vikingi (FastAPI, admin_panel)
Обновлено по состоянию кода в каталоге admin_panel/static и маршрутам admin_panel/main.py
(в т.ч. согласованность «Переводы бота» / «Лиды» — см. раздел 6)

================================================================================
1. Общее
================================================================================

• Назначение: аналитика телефонных разговоров, лиды (Telegram / телефон / MAX),
  качество звонков, загрузка аудио, справочники СТО, журнал голосового бота.
• Вход: GET /login — сессия в cookie admin_session, роль задаётся в БД пользователя.
• Роли (см. admin_panel/auth.py): 1 ОП-менеджер, 2 ассистент СТО, 3 хостес,
  4 рук. ОП, 5 рук. СТО, 6 директор (полный доступ к звонкам/лидам и т.д.),
  8 суперадмин (доп. импорт SPRecord, доступ к «Переводы бота» и API /api/voice-bot/*).
• Часть пунктов меню скрыта по роли (display:none в HTML, затем показ через JS
  по window.ADMIN_ROLE_ID, подставляемому сервером в каждую страницу).

Открывать страницы нужно по адресам приложения (/ , /leads), а не файлом
/static/*.html напрямую — иначе не подставится роль и сломается навигация.

================================================================================
2. Закладки и страницы (навигация)
================================================================================

--- /login ---
Форма входа. После успеха — редирект на главную или на голосовые переводы (если
настроено для узкой роли).

--- /  «Звонки» (index.html) ---
Маршрут по умолчанию после входа для большинства ролей.
• Данные: GET /api/calls — список записей звонков из БД аналитики (calls и связанные поля).
• Фильтры: период дат, отдел (ОП / СТО / Прочие), менеджер, вид звонка (вход/исход и т.д.),
  рабочее/нерабочее время; для СТО — опция узкого слоя STO_TO (чекбокс).
• Таблица: ID, дата, время, номер, отдел, тип, узкий СТО_ТО, источник, балл, статус;
  переход в карточку звонка.
• Карточка звонка: GET /call/{call_id} (call.html) — детали, транскрипт, оценки,
  аудио GET /api/calls/{call_id}/audio, действия (исключить, переклассифицировать и т.п.
  — см. API в main.py).

--- /upload  «Загрузка» (upload.html) ---
• Ручная загрузка WAV/MP3 с компьютера или импорт из каталога SPRecord (если доступно).
• POST /api/upload, для SPRecord — дополнительные endpoint’ы из блока upload/sprecord.

--- /leads  «Лиды» (leads.html) ---
• Данные: GET /api/leads — лиды из telegram_leads (Telegram, телефон, MAX, при необходимости
  синтетика из голосовых сессий без лида — логика в postgresql_manager).
• Фильтры: период, канал (need_type), исход голоса, номера и др.; быстрые кнопки периода.
• Дополнительно: сводка по голосовому боту по дням, непринятые звонки — отдельные API
  /api/leads/report, /api/leads/unanswered (см. main.py).

--- /analytics  «Аналитика» (analytics.html) ---
• Аналитика качества звонков: отдел (ОП/СТО), менеджер, периоды, графики и таблицы.
• Данные: /api/analytics/* (недельная, период, менеджеры, критерии, экспорт и т.д.).

--- /body-calls  «Кузовной цех» (body_calls.html) ---
• Урезанный список звонков для кузовного направления (фильтры по периоду, менеджеру,
  типу СТО/прочие).
• GET /api/body-calls — отдельная выборка для этой страницы.
• Пункт меню показывается ролям 5, 6, 8 (и др. по скрипту на странице).

--- /voice-transfers  «Переводы бота» (voice_transfers.html) ---
• Журнал сессий голосового бота (PostgreSQL: voice_bot_sessions, реплики, события перевода)
  и телефонные лиды (telegram_leads) — подробно раздел 6.
• API: /api/voice-bot/sessions, daily-summary, export, деталка по UUID, запись WAV,
  блок ОКК /api/voice-bot/feedback.
• Период дат и экспорт CSV/XLSX; сводка по дням; таблица «Сессии»; AMI; доступ по роли
  (can_access_voice_transfers — в коде только роль 8).

--- /sprecord-browse  «SpRecord по дате» (sprecord_browse.html) ---
• Просмотр файлов записей на шаре sprecord (путь на сервере вроде /mnt/sprecord),
  фильтр по дате, прослушивание через API с сессией.
• Связь с голосовым журналом описана в тексте на странице (сверка со «Переводы бота»).

--- /sto  «СТО» (sto.html) ---
• Справочники СТО: загрузка/скачивание Excel и превью листов.
• API: /api/sto/files, upload, download, preview.

================================================================================
3. Вспомогательные URL (не отдельные «закладки» в меню всех ролей)
================================================================================

• /call/{call_id} — карточка одного звонка.
• /public/privacy-policy — публичная страница политики (если используется).
• Статика: /static/* — CSS, app.js и т.д.; основная разметка страниц отдаётся через
  HTMLResponse с подстановкой ADMIN_ROLE_ID.

================================================================================
4. Откуда берутся данные (кратко)
================================================================================

• Звонки / карточка / аналитика: таблицы call-аналитики (CallAnalyticsDB и связанные).
• Лиды: telegram_leads и производные представления в PostgreSQL.
• Переводы бота: voice_bot_sessions, voice_bot_transcript_turns, voice_bot_transfer_events,
  заполняются сервисом голосового бота при включённом логировании в БД.
• Файлы SPRecord: файловая система, не БД.

================================================================================
5. Примечание про согласованность дат
================================================================================

Страница «Переводы бота» и API используют календарный день в часовом поясе сессии БД
(POSTGRESQL_SESSION_TIMEZONE / TZ). Фильтры периода на разных страницах должны
интерпретироваться в том же контексте, что и подстановка «сегодня» из /api/admin_config.

================================================================================
6. «Переводы бота»: таблица «Сессии» и сводка по дням (как сделано в коде)
================================================================================

Цель: чтобы числа в сводке на /voice-transfers совпадали с тем, как оператор
считает строки на /leads и в таблице сессий — одна запись лида = одна строка,
«переведено / не переведено» — как колонки «Исход звонка» и «Перевод» у лида
и «Последний перевод» в списке сессий.

Реализация (database/postgresql_manager.py — VoiceBotAnalyticsDB):

--- Таблица «Сессии» (GET /api/voice-bot/sessions, экспорт) — list_sessions ---

• Строка = запись в telegram_leads с источником телефон (COALESCE(source,'telegram')='phone'),
  с LEFT JOIN voice_bot_sessions по telegram_leads.voice_bot_session_id.
• Период: попадает в выборку, если календарный день created_at лида входит в диапазон
  ИЛИ (есть сессия и календарный день started_at сессии входит в диапазон). Так не теряются
  строки, когда дата лида и дата начала звонка по факту расходятся.
• Поле id в ответе — id лида; для экспорта подставляется caller_phone_client из caller_phone.
• Если колонки voice_bot_session_id в БД нет — fallback: список только из voice_bot_sessions
  (старое поведение).

--- Сводка по дням (GET /api/voice-bot/daily-summary) — daily_summary ---

• Первые три числовые колонки считаются по ЛИДАМ, группировка по календарному дню
  created_at лида (как «Лидов (записей)» на странице «Лиды» за тот же день).
• «Записей лидов» (sessions_total в JSON): COUNT(DISTINCT tl.id) для phone-лидов за день.
• «Переведено всего» / «Не переведено (сброс)»: для каждого лида проверка «как в интерфейсе»:
  переведено, если у последнего по времени события voice_bot_transfer_events для сессии
  лида (voice_bot_session_id) непустая transfer_category ИЛИ у лида
  voice_contact_outcome = 'transfer_started'; иначе — в «не переведено» (сброс до перевода,
  в таблице «—»).
• Лид без привязки к сессии учитывается только по полю voice_contact_outcome (категории
  из журнала нет).
• Колонки по отделам (Администратор, Ассистент сервиса, …) — по-прежнему считают события
  с успешным AMI (ami_result = 'transfer_started'), группировка по дню начала сессии
  (started_at::date), отдельным блоком SQL; FULL OUTER JOIN с блоком по лидам по полю day.

Отчёт GET /api/leads/report для страницы «Лиды» подмешивает в voice_daily_summary
поле phone_leads_rows — оно должно совпадать с числом лидов за день из того же принципа
подсчёта строк phone (TelegramLeadsDB.phone_leads_row_count_by_calendar_day).

--- Список лидов на /leads (отдельно от переводов) ---

• После выборки для обычного режима применяется дедуп: одна строка на voice_bot_session_id
  (_dedupe_leads_one_per_voice_session), чтобы не дублировать один звонок в таблице.
• Режим «Непереведённые (для обзвона хостес)»: на клиенте dedupeHostessFollowupRows —
  один номер (последние 10 цифр) → одна строка с самым поздним created_at.
