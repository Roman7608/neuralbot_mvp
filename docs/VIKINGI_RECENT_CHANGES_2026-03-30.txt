# Vikingi — последние изменения и сводка (2026-03-30)

Рабочая копия на server7 (каталог проекта VikingiAll). Ниже — что менялось в коде/БД и
зафиксированные выводы по диагностике DID.

--------------------------------------------------------------------------------
1. КОД: asterisk_transfer.py (AMI DBGet / перевод звонка)
--------------------------------------------------------------------------------

Проблема: в логах было «AMI DBGet: пустой Val» при успешном переводе через fallback.

Причина: в AMI на действие DBGet Asterisk отвечает двумя блоками — сначала
Response: Success (без поля Val), затем Event: DBGetResponse с Val. Старый код
читал только первый блок и терял остаток буфера, если оба блока приходили в
одном recv().

Сделано:
- Добавлен буферизованный разбор AMI (_AmiBufferedReader, _parse_ami_block).
- _ami_dbget_channel читает второй блок DBGetResponse и берёт Val оттуда.
- Сессия AMI (Login → DBGet → Redirect → Logoff) идёт через один читатель.

Файл: asterisk_transfer.py

4. ДИАГНОСТИКА DID (695874 vs 707755) — выводы
--------------------------------------------------------------------------------

- Эталон на 707755: в Asterisk видно Incoming call -> 707755, AudioSocket на
  voice-bot (9092 или 9093 для Jetour), в voice-bot — сессия, при переводе AMI ok.

- Запрос логов по 695874 на Asterisk (grep 695874 / Incoming call в tail) показал:
  в логах контейнера vikingiall-asterisk-1 нет строк с 695874; попадают только
  вызовы с -> 707755 (тот же ANI).

- В extensions.conf все входы from-infolada с номером в EXTEN (шаблон _X.) идут
  в AudioSocket (бот), отдельной ветки «живые запчасти» на этом Asterisk нет.

Вывод для согласования с Инфоладой: вызов на 695874, при котором абонент
дозванивается до живого отдела, с высокой вероятностью не приходит на этот
Asterisk с EXTEN=695874 или идёт другим маршрутом; требуется уточнить у
оператора Request-URI / маршрутизацию DID.
